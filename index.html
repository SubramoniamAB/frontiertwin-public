Pending: runs on Spark, awaiting scores

What "pending" means. These models fit and run on one DGX Spark (memory, speed and deploy commands are known), but no public benchmark scores exist yet for coding, reasoning, knowledge and the other capabilities.

Without scores there is nothing to compare against a paid model, so they are not included in the match %, the ranking table, the closest twin or the matrix.

A pending model joins the ranking automatically once its scores are added (an updated catalog, or ft.py add with "kind": "local"). Models found by ft.py refresh --discover also start here.

What changed

    Loading the model catalog

    Frontier targets, Spark-ready open models and their benchmark scores appear here once data/models.json loads. Start the app with python3 ft.py serve and open http://localhost:8080.

    How matching works

    1 · Capability ratio

    For each capability (BenchLM 0–100), local score ÷ frontier score, capped at 100%. Beating the frontier model on one capability cannot hide a gap in another.

    2 · Your weights

    Match % = Σ (weight × ratio) ÷ Σ weights. Sliders set each weight from 0 (ignore) to 5; the % beside each slider is its share.

    3 · Estimates

    Where a local model only has an overall score, its capability is estimated from that score using the frontier model's profile. Shown as hatched bars.

    4 · Quantization

    Local scores are lowered about 2% at 4-bit, 7% at 3-bit and 12% at 2-bit. NVFP4, MXFP4 and FP8 are treated as native precision.

    5 · Vision gate

    If the frontier model reads images and the local model does not, Vision scores 0 for that pair.

    6 · Fit and speed

    "Fits" = weights plus ~8 GB cache under 119 GB. Speeds are measured single-user decode on a Spark; "est." is computed from active parameters and 273 GB/s.

    Help

    Getting started

    1. Pick the paid model. Choose a vendor tab, then a model. Use the version dropdown beside it (for example Opus 5.5, 5 or 4.8).
    2. Set priorities. Click a preset (Balanced, Coding, Agents, Research, Vision) or move the sliders.
    3. Set constraints. Vision, NVIDIA playbook only, tight fits, minimum context, minimum speed, local version and family.
    4. Read the twin. The right panel shows the closest open model, its match %, capability bars, gaps and hardware facts.
    5. Deploy it. Copy the commands under "Deploy on your DGX Spark".

    The address bar keeps the selected model (for example #claude-opus-5), so you can bookmark or share a view. Press ? anywhere to open this guide, Esc to close it.

    Priorities & sliders

    Each slider sets how much one capability counts in the match % (0 = ignore, 5 = most important). The % at the right of each slider is its share of the score.

    Match % = Σ (weight × capability ratio) ÷ Σ weights

    Capability ratio = local score ÷ frontier score, capped at 100%. A local model that beats the frontier model on one capability cannot make up for a weakness elsewhere.

    Example (Research preset): Reasoning 5, Knowledge 4, Math 3, Agents 2, Coding 1, Vision 1. Total = 16, so Reasoning is 31% of the score and Coding 6%. A model weak at coding loses little; one weak at reasoning loses a lot.

    • Moving a slider re-ranks every model, the closest twin, the table, the matrix and the summary tiles at once.
    • Weight 0 removes a capability from the score; its bar still shows, marked with "·".
    • Sliders change ranking only. Which models qualify is set by the constraints (fit, speed, context, vision, playbook).
    • Moving any slider clears the preset highlight; click a preset to restore its values.

    Reading the results

    VerdictMatch %Meaning
    Near-equivalent≥ 90Can replace the paid model for these priorities
    Close75–90Small, specific gaps
    Partial60–75Usable for some tasks; escalate hard ones
    Distant< 60Not a substitute
    • Bars: purple = frontier model, blue = local model. The number at right is the point difference.
    • Hatched bar: the local model has no published score for that capability; it is estimated from its overall score using the frontier model's profile.
    • Red "no vision": the frontier model reads images and the local model does not; that capability scores 0.
    • Quantization: scores are lowered about 2% at 4-bit, 7% at 3-bit, 12% at 2-bit. NVFP4, MXFP4 and FP8 are not penalized.
    • Fit: "fits" = weights plus about 8 GB cache under 119 GB; "tight" = 2–3 bit quant or over about 95 GB.
    • tok/s: measured single-user decode speed on a Spark; "est." = computed from active parameters and 273 GB/s bandwidth.
    • Pending: a model that runs on a Spark but has no published capability scores yet. It is listed under "Pending" with speed, memory and deploy commands, but is left out of the match %, ranking and matrix until scores exist.
    • Versions: the buttons under the twin score other versions of the same local family against the same target.

    Match matrix

    Every frontier model (rows) against every local model that passes your constraints (columns), scored with your current sliders.

    • Cell = match % for that pair. Darker = closer match.
    • Outlined cell = best local model for that row.
    • Best twin column (right) names it and gives its score.
    • Rows are sorted by frontier overall score; columns by local overall score, strongest first.
    • Click any cell to open that pair in the twin panel.

    How to use it: scan down a column to see which paid models one local model can stand in for; scan across a row to compare local options for one paid model. Bottom rows (small paid models) usually show the highest scores, meaning those are the easiest to replace locally.

    Deploy on DGX Spark

    Below the twin, pick a runtime tab and click Copy. A ✓ on a tab means an official NVIDIA DGX Spark playbook covers that model on that runtime; the green badge links to the playbook.

    RuntimePortNotes
    vLLM8000NVIDIA container; OpenAI-compatible API. Default choice.
    SGLang30000Adds --quantization modelopt_fp4 for NVFP4 models
    TRT-LLM8355Highest throughput; NVIDIA's TensorRT-LLM container
    llama.cpp30000GGUF files; one-time CUDA build for GB10
    Ollama11434Simplest install; fewer tuning options
    NIM8000Prebuilt NVIDIA container; needs an NGC API key
    Chat UI3000 / 8080Open WebUI in front of the server
    1. Create a Hugging Face token (huggingface.co/settings/tokens) and replace <your_hf_token>.
    2. If the handle shows verify on Hugging Face, confirm the exact repository name first.
    3. Run the block on the Spark; the health loop waits until the model is loaded (large models: several minutes).
    4. Test with the included curl, then point your tools at http://<spark-ip>:<port>/v1.

    --max-model-len is capped at 131072 to keep memory in budget; raise it if the model is small.

    Refresh & live updates

    Automatic: open pages re-read the catalog every 60 seconds and when the tab regains focus. No reload needed.

    Manual: click the refresh icon in the header. On a self-hosted server it rebuilds the catalog (merging catalog_url if set) and reloads the data. In offline file mode it reloads the page.

    Status chip: green = data refreshed within 10 days; amber = older or unreachable.

    Command line (self-hosted)

    python3 ft.py refresh                     # rebuild + apply your overrides
python3 ft.py refresh --discover          # add new Spark-sized models from Hugging Face
python3 ft.py refresh --catalog URL       # merge a newer shared catalog
python3 ft.py add my-model.json           # add or correct a model

    Scheduled refresh

    # Ubuntu / DGX OS / macOS (crontab -e): Mondays 10:17
17 10 * * 1 cd /opt/frontiertwin && python3 ft.py refresh --discover >> refresh.log 2>&1

# Windows
schtasks /create /tn "FrontierTwin Refresh" /sc weekly /d MON /st 10:17 /tr "py -3 C:\frontiertwin\ft.py refresh --discover"

    Full options, systemd timer and Docker variants: HOW_TO_RUN.md, sections 9–11.

    Install & upgrade

    Dockerdocker compose up -d --build
    Servicesystemd unit frontiertwin.service
    No serverdouble-click index.html (offline, no auto-refresh)

    Open http://localhost:8080 or http://<spark-ip>:8080. Options: --host, --port, or config.json.

    Changing the port

    • In the page (self-hosted): gear icon → Settings → enter a port → Check port → Apply and move. The server starts on the new port, saves it to config.json and the page opens the new address. If the port is taken, you get a message and a suggested free port.
    • At start-up: if the saved port is busy, start.sh / start.bat asks for another port in the terminal (Enter accepts the suggestion). As a service with no terminal, the next free port is used and printed in the log.

    Upgrade

    python3 ft.py check-update                 # needs update_manifest_url in config.json
python3 ft.py upgrade --from frontiertwin-x.y.z.zip
python3 ft.py rollback                     # restore previous version

    Upgrades back up the current install, keep config.json, overrides.json and newer data. Restart the server afterwards.

    Step-by-step for every OS: HOW_TO_RUN.md. Summary: README.md.
